# Agent-friendly 代码库会不会牺牲人类可理解性？

上一篇文章里，我写到一个判断：AI 不只是在写代码，它正在重塑代码的形状。

这句话如果继续往工程里落，就会遇到一个更具体的问题：当我们开始有意识地把代码库改造成 AI Agent 更容易工作的环境，会不会反过来让人类更难理解它？

这个问题不能简单回答“会”或“不会”。

很多 agent-friendly 的做法，本来就是好工程实践。清楚的 README、稳定的测试命令、可复现的本地环境、明确的模块边界、可搜索的文档、可回滚的脚本，这些东西不只是给 AI Agent 用的，也会让新人、值班的人和未来的自己少踩坑。

Agent 能工作，常常意味着团队终于把过去藏在脑子里的隐性知识写了出来。某个服务怎么启动，某个测试为什么必须跑，某个配置为什么不能改，某个发布前检查为什么重要，这些过去靠口口相传的东西，会被迫变成文档、脚本、测试和约束。

从这个角度看，agent-friendly 不但不会削弱人类理解，反而可能提高代码库的工程卫生。

但问题也在这里：**agent 能顺利操作一个代码库，不等于人类真正理解这个系统。**

> **核心判断：** Agent-friendly 不必然牺牲人类可理解性。真正危险的不是代码库变得更适合 AI Agent，而是团队把“agent 容易修改”误当成“人类容易理解、系统容易接管”。



## Agent 需要的，和人需要的，不是同一种理解

我们先把几件事分开。


| 维度       | 关心的问题                | 典型信号                       |
| -------- | -------------------- | -------------------------- |
| **可操作性** | agent 能不能在代码库里行动     | 搜得到入口、跑得起测试、看得懂报错、能根据反馈继续改 |
| **可理解性** | 人能不能重建系统的心智模型        | 说得清模块边界、业务约束、失败模式和设计假设     |
| **可接管性** | 换人或换 agent 后还能不能安全继续 | 能重构、能迁移、能处理事故，而不是只能小修小补    |


这三件事有关联，但不是一回事。

一个代码库可以对 agent 很友好：文件名规整，测试命令明确，错误信息清楚，任务拆分很局部，改一处就能过 CI。Agent 在里面会很顺手，因为它最擅长在清晰反馈下做局部搜索。

但这不代表人类也理解了它。人类理解系统，不只是找到文件和改对一行代码。人类需要把局部实现放回更大的结构里：业务约束是什么，失败模式是什么，哪些边界是历史偶然，哪些边界是不能轻易破坏的设计选择。

程序理解研究很早就指出，维护代码时，人不是简单从上到下读完源码，而是在不断建立和修正 mental model：先形成假设，再用代码、命名、调用关系和运行行为验证假设。代码可读性研究也说明，可读性并不是纯粹的格式问题，它和人的判断、命名、结构、局部复杂度都有关。

Agent 的“理解”更像另一种东西。它可以在足够好的工具和反馈里，把问题拆成局部动作，然后通过测试和日志确认自己有没有偏离。它不一定需要像人一样拥有稳定的全局心智模型，至少在很多日常任务里不需要。

这就是冲突的根源：**agent-friendly 优先优化的是行动路径；human-friendly 更需要解释结构；真正可靠的工程系统，还必须经得起接管。**

## 像给导航系统改造城市

可以把代码库想象成一座城市。

如果城市要对导航系统更友好，它会做很多好事：道路命名更标准，路口标识更清晰，红绿灯数据更准确，施工信息更及时，地图更新更快。对人当然也有帮助。

但如果城市只围绕导航系统优化，就会慢慢出现另一个问题：导航很会告诉你怎么走，却不一定帮助你理解这座城市。

一个熟悉城市的人，靠的不只是路线。他知道哪个街区是什么功能，哪里容易堵，哪些小路夜里不适合走，哪里看起来绕其实更稳，哪里出问题可以临时掉头。他有地标，有经验，有方向感，也知道一些地图上没有写明的历史原因。

代码库也是这样。

Agent 需要的是可搜索的地图、明确的入口、可执行的路线、快速反馈的交通灯。人类还需要知道为什么这条路存在，为什么这里不能修高架，为什么某个看起来奇怪的路口其实是在为历史包袱、事故经验或未来扩建留空间。

如果我们只把代码库改造成 agent 的导航环境，它可能越来越适合自动行驶，却越来越不适合人类形成方向感。


## 机械的 agent-friendly 会把设计意图切散

最容易出问题的，是一种机械理解：**文件越短越好，函数越小越好，目录越规整越好，任务越局部越好，测试越快越好。**

这些东西很多时候确实有价值。短文件降低阅读负担，小函数更容易测试，局部任务更适合 agent 执行，快速测试能让反馈循环跑起来。

但它们不是目的。**把代码切碎，不等于把系统讲清楚。**

Parnas 在 1972 年那篇经典模块化论文里，批评过一种常见做法：按处理步骤把系统切成输入、处理、输出等模块。这样看起来很自然，也很方便分工，但真正好的模块化标准，不是把执行流程切碎，而是把可能变化的设计决策隐藏起来。

换句话说，模块不是“代码块”，而是一种责任边界。一个模块之所以存在，是因为它封装了某个将来可能变化、需要被隔离的判断。

这对 agent 时代尤其重要。

Agent 很适合做局部修改，于是团队可能会无意识地把代码库切成更适合局部修改的形状。一个功能被拆成很多小文件，每个文件都很短，每个函数都很清楚，每个测试都能快速定位失败。短期看，这很好。

但如果这些切分不是围绕变化原因、业务不变量和设计决策来做，而只是围绕“agent 更容易找到和修改”来做，设计意图就会被切散。

人类看到的是一堆局部正确的小片段，却很难回答更关键的问题：

- 这些片段共同维护的约束是什么？
- 哪些地方可以改，哪些地方只是看起来可以改？
- 这个边界是业务边界、性能边界，还是历史偶然？
- 如果需求方向变了，应该替换哪个抽象，而不是到处打补丁？

这类代码库可能很整洁，但不是很好懂。**它让 agent 很容易走到下一步，却不一定让人看清整张地图。**

## Prompt 文件膨胀不是知识沉淀

另一种风险，是把所有知识都塞进 agent 指令文件。

有了 AGENTS、CLAUDE 或类似文件以后，团队很容易把它当成新的工程垃圾桶：这里写一点风格偏好，那里写一条测试命令，再加几个历史坑、几个安全红线、几个 review 习惯。后来发现 agent 还是会犯错，就继续往里面加规则。

最后这个文件变成一个很长的说明书。它看起来像知识沉淀，其实可能只是把隐性知识换了一个地方堆起来。规则太多以后，agent 未必能抓住重点，人类也不愿意维护。更麻烦的是，它可能和真实代码、脚本、架构文档慢慢漂移。

OpenAI 在 agent-first 工程实践里提到过一个经验：给 agent 的不应该是一份巨大的说明书，而应该是一张地图。短入口文件负责指路，真正的知识应该落在更稳定、更可验证、更有所有权的地方：架构文档、设计记录、测试、脚本、规格、运行手册。

这个判断对人同样成立。

好的 agent-friendly 不是把所有东西写给 agent 看，而是把知识放回它应该在的位置：

- 运行方式应该在脚本和 README 里。
- 架构约束应该在架构文档和模块边界里。
- 设计取舍应该在 ADR 里。
- 业务不变量应该在测试和规格里。
- 安全红线应该在 CI、权限和 review 规则里。

**Agent 指令文件更像城市入口的导览牌，而不是城市本身。**

## 测试不是只给 agent 过关的奖励函数

Agent 时代，测试的重要性会继续上升。

原因很直接：agent 需要反馈。没有测试、构建、lint、类型检查、截图、日志，agent 很容易陷入猜测。一个清楚的失败信号，能让 agent 快速收敛到正确修改。

但这也带来一个危险：**测试会被当成奖励函数。**

如果测试只覆盖 happy path，只检查表面行为，只验证“当前 issue 能不能关掉”，agent 就会优化这些测试。它不一定是在作弊；它只是沿着系统给它的反馈前进。

人类也会这样。团队如果只奖励测试通过和 PR 合并速度，工程师也会倾向于写更容易通过的测试，而不是更能表达系统不变量的测试。

所以工程篇里最关键的一点是：**测试不只是验证工具，也是理解工具。**

好的测试应该告诉后来的维护者：这个系统真正不能破坏的性质是什么。比如金额不能凭空增加，权限不能绕过，状态迁移不能倒退，幂等接口不能产生重复副作用，重试不能扩大事务边界。

QuickCheck 这类 property-based testing 的价值就在这里。它不是只列几个例子，而是把系统应该满足的性质写出来，再用大量生成样例去找反例。TLA+ 这类形式化规格更进一步，把并发、状态迁移和安全属性放到实现之前讨论。

不是每个项目都需要形式化方法。但每个项目都可以吸收这个思想：测试应该尽量表达不变量，而不只是复现当前实现。

对 agent 来说，这会提供更好的反馈。对人来说，这会留下更清楚的系统意图。

## 设计记录是给未来接管者的

很多代码库最难懂的地方，不是代码本身，而是缺少历史。

你看到一个奇怪的抽象，不知道它是深思熟虑后的边界，还是当时为了赶进度留下的折中。你看到一个重复实现，不知道它是技术债，还是为了隔离两个变化节奏不同的业务。你看到一个看似多余的校验，不知道它是历史事故之后补上的保护，还是早该删除的旧逻辑。

Agent 更容易放大这个问题。

它很擅长根据现状推断模式，然后延续模式。如果代码库里没有设计记录，它会把“现在长这样”理解成“应该继续这样”。人类也一样，只是人类可能会去问老同事，而 agent 没有这个通道。

这就是 ADR 这类架构决策记录的价值。它不需要写成长篇论文，只要记录几个关键问题：当时面对什么选择，为什么选这个方案，放弃了什么，未来什么情况下应该重新评估。

这些记录对 agent 有用，因为它能避免 agent 重复挑战已经讨论过的边界。对人更有用，因为它让后来者知道：这个系统不是自然长成这样的，它是由一系列可以被理解、可以被质疑、也可以被修正的决策构成的。

**可理解性不是把代码写得像白话文。** 它很大一部分来自可追溯性：后来的接管者能不能从代码、测试和记录里还原设计意图。

## 好的 agent-friendly 和坏的 agent-friendly

所以，问题不在于要不要 agent-friendly。

未来的代码库大概率都要对 agent 友好。拒绝这一点没有意义。真正要区分的是：什么样的 agent-friendly 也会增强人类理解，什么样的 agent-friendly 只是在提高自动修改速度。

我会用五条标准来判断。

**第一，好的 agent-friendly 会让隐性知识显性化；坏的只会堆规则。**

如果一个团队把运行、测试、发布、回滚、设计约束写进脚本、文档、测试和 CI，这是进步。如果只是不断往 prompt 文件里追加“注意事项”，那只是把口口相传换成了文件相传。

**第二，好的 agent-friendly 会强化模块边界；坏的会把设计意图切散。**

模块边界应该围绕变化原因和责任划分，而不是围绕当前任务怎么更容易被 agent 局部修改。短文件和小函数有价值，但它们不能替代架构判断。

**第三，好的测试表达不变量；坏的测试只是让 agent 过关。**

测试越像业务契约，越能同时服务 agent 和人类。测试越像一次性验收脚本，越容易变成局部优化的奖励函数。

**第四，好的文档解释为什么；坏的文档只告诉 agent 怎么做。**

“运行 `make test`”很重要，但它只解决操作问题。“为什么这个模块不能绕过这层接口”“为什么这里必须强制校验权限”“为什么这个队列允许延迟但不能丢消息”，这些才是理解问题。

**第五，好的 agent-friendly 最终提高可接管性；坏的只提高自动修改速度。**

如果 agent 修改速度越来越快，但人类越来越难解释系统，越来越不敢重构，越来越只能让 agent 继续修 agent 造成的问题，那不是工程能力增强，而是理解成本被延后了。

## 最高目标不是可读，而是可接管

“人类可理解性”这个词，容易让人想到代码是否好读。

但在 agent 时代，单纯“好读”已经不够了。

局部代码可读，只说明你能看懂一段实现。系统可理解，说明你能重建模块意图和依赖关系。**真正关键的是可接管：当系统处在压力、变化和事故里，人类还能不能介入并承担责任。**

这也是为什么我不太愿意把工程篇写成“如何让代码对人和 AI 都友好”的技巧清单。技巧当然重要，但更重要的是判断标准。

一个代码库是否真的 agent-friendly，也 human-friendly，可以问四个问题：

- 人能否说清这个模块为什么这样切？
- 测试是否表达了不变量，而不只是覆盖 happy path？
- 后来者能否看到关键设计决策的历史？
- 换一个 agent 或换一个人，系统还能不能被安全接管？

如果答案是否定的，那么 agent 在里面跑得再顺，也只是说明这座城市对导航系统很友好，不说明人类还认识这座城市。

## 结尾

Agent-friendly 代码库不会天然牺牲人类可理解性。恰恰相反，很多时候它会逼着团队补上过去欠下的工程债：明确入口，稳定脚本，补齐测试，记录约束，让隐性知识变成共享资产。

但它也会诱导一种新的局部最优：把代码库改造成更适合机器搜索、试错和局部修补的环境，然后误以为这就是更好的工程。

**真正好的 agent-friendly 代码库，应该让 agent 更容易行动，也让人类更容易接管。** 它不只是给机器铺路，也给人留下地标、边界、历史和紧急出口。

如果一个系统只提高了自动修改速度，却降低了人类重建心智模型的能力，那它不是更先进，只是把理解成本推给了未来。
